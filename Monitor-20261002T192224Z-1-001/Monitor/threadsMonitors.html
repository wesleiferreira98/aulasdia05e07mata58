Monitors and Synchronization

Recall that all threads in a program share one heap. This means that they can all see, and interact with all the objects in the program. (On the other hand, each thread has its own stack for local variables.) In many cases this sharing does not matter. Each thread references only objects that other threads do not reference. In this case each thread goes on its merry way without interfering with any other thread. However, when threads interact with the same object, trouble in the form of strange bugs can arise.

Mailbox Example

Consider a simple mailbox. The mailbox has state. In one state there is no mail. In the other state, mail has arrived. The mailbox has a boolean variable, youHaveMail to reflect its state, and an array of characters to hold any message that has arrived. This being a vary small mailbox, it can only hold 72 characters.

There is one owner of the mailbox who is so anxious that he checks his mail every 20 milliseconds. The owner of the mailbox has two friends who send one line messages at random intervals.

The consumer of messages (the owner of the mailbox) and the two message producers are represented as independent threads. As all three threads attempt to read and write to the one mailbox object you can expect trouble!

The monitor

Java uses the monitor concept as the basis of its thread synchronization. A monitor is an object that can block and revive threads.

A Monitor analogy.

A gas station has a single toilet the key for which is kept at the service desk. This is a shared resource for passing motorists. To use this shared resource the prospective user must acquire a key to the lock on the toilet. The user goes to the service desk and acquires the key opens the door, locks it from the inside and uses the facilities.

Meanwhile, if a second prospective user arrives at the gas station he finds the toilet locked and therefore unavailable to him. He goes to the service desk but the key is not there because it is in the hands of the current user. When the current user finishes, he unlocks the door and returns the key to the service desk where it is given to the waiting customer. If more than one prospective user turns up while the toilet is locked, they must form a queue waiting for the key to the lock.

Obviously in applying this analogy to Java, a Java thread is a user and the toilet is a block of code which the thread wishes to execute. Java provides a way to lock the code for a thread which is currently executing it, and making other threads that wish to use it wait until the first thread is finished. These other threads are placed in the waiting state. Java is not as fair as the service station because there is no queue. Any one of the waiting threads may get the monitor next, regardless of the order they asked for it. The only guarantee is that all threads will get to use the monitored code sooner or later.

The synchronized keyword.

A block of code can be turned into a monitor using the keyword synchronized.

There are two ways to use synchronized

Synchronizing a whole method by adding the word synchronized as a modifier in the method's header. This is the most common way of doing it. Many of Java's API methods are synchronized this way. For example, public synchronized void setLabel(String label) from the Button class. The object referenced in the method call is the object holding the lock, in this case the Button object.

Synchronizing only a block of code within a method using the synchronized keyword. The block of code is preceded by the keyword synchronized and an expression which references the object holding the lock. For example, here is a code fragment which changes all values in an array to positive and prevents any other thread from changing any elements before the code has finished making all the changes.

    public void static absolute(int [] values) {
    synchronized (values) {
    for(int i=0; i < values.length; i++) {
    if(values[i] < 0)
    values[i] = -values[i];
    }
    }
    }

wait(), notify() and notifyAll()

Looking at the output of the synchronized version Mailbox3g.java you can see that the anxious consumer often goes to the mailbox and is disappointed because no mail has arrived. It would be nicer, and more efficient, if the consumer waited until notified that a message has arrived.

The methods wait(), notify() and notifyAll() service this need. Note that all three can only be used within synchronized code. If you try to use them outside of synchronization you will get a compiler error. Note that these methods belong to the Object class, not the Thread class.

public final void wait() throws InterruptedException
public final native void wait(long timeout) throws InterruptedException

wait() puts the current thread into the waiting state.

public final native void notify()

notify() looks at the threads in the waiting state, and picks one (which one is unpredictable) and moves it to the ready state where the scheduler will decide what to do with it. Any other threads in the waiting state remain there until notify() or notifyAll() are called again.

public final native void notifyAll()

notifyAll() moves all the threads in the waiting state into the ready state where the scheduler will decide when they will move to the running state. NotifyAll() is much more commonly used than notify() because the latter could conceivably leave a thread waiting for a very long time if it were unlucky.
